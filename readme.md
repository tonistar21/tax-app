# NYS Sales Tax Automation & Filing System

B2B-система для розрахунку та підготовки податкової звітності (Sales Tax) для штату Нью-Йорк. Головна фіча — використання PostGIS для точного визначення податкових юрисдикцій за координатами доставки та автоматична генерація заповненої форми ST-100 для податкової.

## Що під капотом (Стек)

* **Backend:** Node.js, Fastify, TypeScript.
* **База даних:** PostgreSQL + PostGIS.
* **ORM:** Prisma (з використанням `$queryRawUnsafe` для просторових запитів).
* **Frontend:** React, Vite, Tailwind CSS.
* **Робота з PDF:** `pdf-lib` (попіксельний рендеринг поверх растру).
* **Інфраструктура:** Docker & Docker Compose (із вбудованим завантаженням GeoJSON).

## Основний функціонал

1. **Гео-розрахунок податків:** Визначення округу (County), міста та ставки податку за координатами (Lat/Lon).
2. **Масовий імпорт:** Завантаження тисяч транзакцій через CSV з автоматичною валідацією.
3. **Ledger:** Посторінковий перегляд транзакцій, Subtotal та Tax Collected.
4. **Агрегація даних:** Зведення мільйонів транзакцій до конкретних кодів звітності (Reporting Codes) NYS.
5. **Експорт ST-100 PDF:** Точне накладання цифр на офіційний бланк штату + генерація детального додатка (Worksheet) для аудиту.

## Архітектурні та бізнес-рішення

Проєкт писався під реалії податкового законодавства США. Ось як ми вирішили основні крайові кейси:

### 1. Нульова ставка для замовлень поза штатом (Out-of-State)

Якщо координати не перетинають полігони штату Нью-Йорк, транзакції присвоюється статус `OUT_OF_STATE` і ставка 0%.
**Чому так:** Податок із продажу в США стягується за місцем доставки (Destination-based sourcing). Спираючись на прецедент Верховного суду *South Dakota v. Wayfair*, якщо товар їде за межі Нью-Йорка (і там немає "нексусу"), податок штату не застосовується.

### 2. Обробка "водних" координат

Якщо точка доставки опиняється у воді (річка Гудзон, прибережна зона Атлантики), система не падає і не ставить 0%, а шукає найближчий полігон суші алгоритмом Nearest Neighbor (`ORDER BY geom <-> point LIMIT 1`).
**Чому так:** Товари можуть доставлятися на яхти або комерційні судна (наприклад, кур'єрами на катерах чи дронами). Судноплавні води належать до юрисдикції штату, і доставка на пришвартоване судно обкладається податком найближчого округу.

### 3. Склеювання Нью-Йорка (NYC Aggregation)

Система автоматично зводить 5 різних районів (Bronx, Kings/Brooklyn, New York/Manhattan, Queens, Richmond/Staten Island) в один рядок із кодом `8081`.
**Чому так:** Хоча географічно це 5 різних округів (Counties), податкова вимагає об'єднувати їх у формі ST-100 під єдиним неймінгом *«New York City/State combined tax»*.

### 4. Overlay замість AcroForms для генерації PDF

Дані малюються поверх PDF за жорстко відкаліброваними координатами X/Y (із динамічним масштабуванням шрифту), а не вставляються в поля форми.
**Чому так:** Офіційний бланк ST-100 від Департаменту податків — це плоский растр. У ньому немає стандартизованої структури `/AcroForm`. Накладання тексту через `pdf-lib` — єдиний стабільний спосіб автоматизувати заповнення цього бланка без ризику, що документ не пройде машинне зчитування в податковій.

## Як працює гео-рушій

При імпорті CSV бекенд проганяє такий SQL-запит для кожної точки:

1. Конвертує Lat/Lon у геометрію: `ST_SetSRID(ST_MakePoint(lon, lat), 4326)`.
2. Перевіряє `ST_Contains` для міст-винятків (`geo_city_exceptions`).
3. Якщо міст немає — перевіряє перетин із полігонами округів (`geo_counties`).
4. Якщо перетину немає взагалі — фолбек на `<->` для прив'язки до берега.

## Запуск локально

Все запаковано в Docker, додаткові залежності на хості не потрібні.

```bash
docker compose up --build -d

```

**Що відбувається при старті:**

1. Піднімається PostGIS.
2. Контейнер `server` накочує міграції Prisma.
3. Скрипт `load-geo.js` створює таблиці та заливає полігони штату з `data/geo/*.geojson`.
4. Клієнт доступний на `http://localhost:5173`.
